**交付目标与边界**

所有 agent 在各自当前已获授权的仓库工作区执行任务，以 `git rev-parse --show-toplevel` 确认仓库根目录。正文代码路径相对于仓库根目录，文档链接相对于所在文档目录；执行不依赖统筹的本机路径。

先交付“可信版本数据与可回滚发布”的可运营内测版，再推进学习/复盘产品。保留模块化单体，落实独立数据包、完整快照、共享会话、双实例发布与同补丁灰度。进程内多快照、图片复盘、legacy 删除和跨主机扩容都有任务，但由明确条件启动。

当前进度：内测必选工程任务 23 项，已完成 0；后续产品演进 2 项，已完成 0；条件演进 4 项，尚未启动。本轮已经产出计划/架构/任务卡/审查模板，这不等于任何业务任务已完成。角色只是推荐分工，用户尚未把具体 agent 指派到任务。

**总体架构由统筹维护**

| 责任角色 | 负责范围 | 协作原则 |
| --- | --- | --- |
| C：当前统筹/Reviewer | ADR、接口边界、依赖排序、跨模块一致性、dev 验收和台账 | 只有通过对应提交的验收，才将任务改为已完成 |
| D：数据 agent | 来源适配、规范 ID、manifest、校验、版本语义、构建包 | 不直接覆盖生产目录；共享契约与 C/B 协调 |
| B：后端 agent | RuntimeSnapshot、AppService、身份/额度、状态、证据、性能 | 不按请求重编译 Graph，不让模型补缺失事实 |
| R：交付 agent | 构建、CI、容器/systemd、代理、发布控制与回滚 | 对脚本、镜像、数据、实例状态共同负责 |
| U：客户端 agent | HTML 清洗、证据卡片、反馈和会话状态展示 | 使用已定义的证据协议，覆盖 Web/Wails |
| Q：质量 agent | fixture、事实评测、故障演练、跨模块回归 | 独立验收实际行为，不以文案关键词代替正确性 |

同一个 agent 可承担多个角色，但每个任务同时只有一个主负责人。初期建议最多三条活跃实现线，优先数据、交付、质量；前端安全可替换其中一条或下一批执行。增加 agent 数量不会消除接口和共享文件依赖。

**状态流转与进度计算**

```text
可分派/待前置 → 进行中 → 待审查 → 分支验收通过 → 待 dev 验收 → 已完成
                         ↓需修改                     ↓需修改
                       进行中                      进行中
```

“阻塞”须记录实际阻塞项、负责人、下一步和影响，不能只写“还没做”；“待前置”表示正常依赖未完成。“分支验收通过”不等于合入 dev，“合入 dev”也不等于线上已发布。上线环境、部署 ID、data release 和演练结果单独记录。

只有以下条件全部满足，C 才将任务改为“已完成”：有明确 dev 提交包含任务；实现符合 ADR 与任务验收；相关检查通过或有明确不适用说明；没有未关闭的阻断发现；涉及发布/用户行为的任务有对应环境或端到端证据。文档任务只验文档，不冒充代码能力。

本计划不按 agent 的口头百分比汇总。进度显示“已完成数量/当前阶段任务数、正在做的 ID、阻塞 ID、最近审查提交、待验收项”。估算区间仅用于排期，不以加总文件行数、提交数或 PR 数代表进度。

**后续 dev Review 的入口**

用户可以提供任务 ID + PR/提交，或直接说“review 最新 dev，更新计划”。C 随后获取远端、记录精确基准/目标提交、保护工作区修改，按[Review 台账](DEV_REVIEW_LOG.md)的流程执行。不会仅凭提交标题将任务标记完成；有新增代码也可能仍是部分实现。

本计划不创建后台监控或自动发布任务。每次收到交付或 review 指令时更新进度、依赖与下一批可分派任务；没有新审查证据时保持现有状态。
